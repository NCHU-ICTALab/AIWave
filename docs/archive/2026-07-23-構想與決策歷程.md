## 企業背景（統一資訊）

統一資訊自 **1997 年**成立，深耕企業資訊服務，客戶留存率達 **86%**。旗下平台整合了清潔、修繕、寄件、餐廳訂位、美食外送、商城購物等生活服務，總服務規模超過 **12,000 家**，114 年營業額年成長 **35%**。

目前統一資訊正積極導入 AI 技術、大數據分析、生成式 AI 與語音服務，試圖解決「服務多元化但客戶體驗不一致」的挑戰，目標是在 AI 時代提供跨平台、跨服務的全方位生活支援。

## 命題目標（直接摘自 PDF）

> **AI 生活管家：智慧社區服務需求理解與媒合平台**
> （命題類別：智慧零售。註：本段早期誤記為「智慧生活服務需求主動滿足平台」，2026-07-23 對照官方命題文件更正。官方核心＝彈性留資表單＋服務媒合＋廠商後台。）

### 命題說明

**核心概念**：「智能生活服務管家」。統一資訊將提供生活服務相關的 API，包含：

- 居家（清潔）
- 居家（修繕與相關服務）
- 居家（地圖及居家服務）
- 居家（App 串接）
- 電商（i 電商 EC 購物）
- 食（飲食服務）

平台已開發智能管家服務，可透過語音或自然語言的互動方式，滿足使用者的生活服務需求。

**競賽目標**：評委以「讓用戶使用者」的角度去體驗，希望看到智能生活管家的應用，並透過技術賦能下做一個好的互動。

### 具體應用場景（命題指定）

平台將針對以下生活服務管理服務，清潔、水電修繕及居家服務諮詢 C 端平台，參賽者需如下：

**(i) 消費者：使用者體驗。**

消費者可透過文字或語音方式需求，讓智能管家下達不同的功能，例如清潔、商品購買、地圖服務、資訊查詢、居家服務諮詢等功能，並以不同服務情境整合提供良好的使用者體驗。

**(ii) 合作服務廠商：上層系統協調消費者。**

合作服務廠商可透過後台查詢消費者需求、諮詢單內容、協調信件發佈及訂單狀態，並進一步協調消費者與廠商完成。

參賽者也可進一步設計附帶訂單管理功能，例如訂單異動、需求開單、訂單管理、回覆客戶及服務進度更新等。

**(iii) 設計後台：包含服務諮詢單、服務廠商管理後台。**

設計後台可包含不同服務項目所需的諮詢單整理、服務商業資料管理、訂單管理、消費者需求 C 端功能相關的系統作業功能。

參賽者可進一步設計服務每日推播，例如根據服務歷史、地區、時段、天氣、節慶或促銷活動等條件，自動生成個性化的服務推薦或商品。

### 參賽者可擴充的方向（命題鼓勵）

參賽者可善用更多智能管家應用，例如在線上生活服務規模、商品與服務推薦、訂單進度通知以及個人化購物互動與設計，更好的融合應用和使用。另外參賽者可根據實際資料格式，自行建立管理後台的測試及平台可使用。

## 資料集解讀（重點整理）

### 訂單完整流程（水電修繕）

```text
用戶描述問題 → 提交諮詢單 (pms_form_feedback)
  ↓ 平台媒合師傅
現場勘驗預約 → mms_order_record (order_status: 12，收訂金 NT$300)
  ↓ 師傅到場後
報價單生成 → quote_no 建立，等待用戶確認
  ↓ 用戶確認
服務進行 → confirm_time 記錄
  ↓ 完工
服務完成 (order_status: 80) / 部退 (98) / 全退 (99)
```

### 訂單類型對照

| order_type | 說明 | 範例服務 |
| --- | --- | --- |
| 01 | 一般服務訂單 | 清潔、水電修繕 |
| 02 | 訂位服務 | 餐廳訂位（EzTable 整合） |
| 07 | 商城購物 | 統一特選咖啡兌換券、美妝商品 |

### 訂單狀態碼

| order_status | 說明 |
| --- | --- |
| 12 | 待確認（已付訂金，等待師傅確認） |
| 80 | 已完成 |
| 90 | 取消中 |
| 98 | 部分退款完成 |
| 99 | 全額退款完成 |

### 個資保護

- 姓名、手機、Email、地址：AES-256 GCM 加密（bytea 欄位）
- 識別同一用戶：使用 `*_hash` 欄位（SHA-256 hash）

## 我們可以做什麼？

### 核心定位

> **「一句話搞定生活大小事的 AI 管家」**

用戶說「我家冷氣很髒，幫我約清洗，順便查一下上次水電的費用，週五再幫我訂個三人的牛排館」— AI 管家一次處理所有事，並在服務進度更新時主動通知。

### 三個角色對應的功能設計（對應命題的三種角色）

#### 角色一：消費者端（C 端）

**UI 形式**：聊天介面（Text + 可選 Voice）

| 功能 | 描述 | 使用的資料 |
| --- | --- | --- |
| 自然語言下單 | 「我家洗衣機很臭」→ 辨識需求 → 建立諮詢單/訂單 | `pms_form`、`mms_order_record` |
| 多服務串聯 | 「搬家前幫我排清潔+寄件+水電檢查」 | 跨 service_id 多筆訂單 |
| 訂單查詢 | 「我上次水電修了多少錢？」 | `mms_order_record` 歷史查詢 |
| 主動通知 | 報價出來了、師傅明天要來、訂單完成 | `order_status` 輪詢/webhook |
| 服務推薦 | 換季提醒清冷氣、春節前打掃提醒 | 歷史訂單 + 時間/地區邏輯 |

#### 角色二：合作服務廠商端（B 端）

**UI 形式**：後台管理頁面

| 功能 | 描述 |
| --- | --- |
| 諮詢單收件 | 查看 `pms_form_feedback` 中新進的客戶需求 |
| 訂單狀態管理 | 更新 `order_status`（確認/完成/取消） |
| 報價單開立 | 填寫 `order_items`（材料費 + 施工費）並通知用戶 |
| AI 輔助回覆 | 根據諮詢單問題，生成建議回覆草稿 |

#### 角色三：設計後台（管理者）

**UI 形式**：數據儀表板

| 功能 | 描述 |
| --- | --- |
| 服務推播設計 | 根據歷史資料設定個性化推送規則 |
| 服務商管理 | `cms_homepage_service_vendor` 的服務項目維護 |
| 訂單分析 | 各服務類型的訂單量、金額、完成率分析 |
| 地區熱度圖 | 結合 `sys_county/district` 分析各地需求分佈 |

## MCP Server 設計規劃

### MCP Server 1：`life-services-mcp`（核心服務查詢）

C 端 AI 管家使用，負責服務目錄與地區查詢。

| Tool | 功能 | 對應資料 |
| --- | --- | --- |
| `list_services(category?)` | 列出所有服務項目，可篩選分類 | `cms_homepage_service` + `cms_homepage_service_vendor` |
| `get_service_detail(service_id)` | 查詢單一服務的詳細資訊與圖片 | `cms_homepage_service` |
| `search_services(keyword, district?)` | 自然語言搜尋服務（「水電」→ 修繕服務） | `cms_homepage_service` + `sys_district` |
| `get_service_form(service_id)` | 取得該服務的諮詢單欄位定義 | `pms_form` + `pms_form_topic` |
| `list_districts(county_id?)` | 查詢縣市/區域清單（用於服務地區選擇） | `sys_county` / `sys_district` |

---

### MCP Server 2：`order-management-mcp`（訂單生命週期）

涵蓋從諮詢單到訂單完成的完整流程。

| Tool | 功能 | 對應資料 |
| --- | --- | --- |
| `submit_inquiry(service_id, form_data, location)` | 提交諮詢單（建立 `pms_form_feedback`） | `pms_form_feedback` |
| `create_order(service_id, user_hash, ...)` | 建立服務訂單（付訂金，`order_status: 12`） | `mms_order_record` |
| `get_order_status(order_no)` | 查詢訂單狀態與進度 | `mms_order_record` |
| `list_user_orders(user_hash, status?)` | 列出用戶歷史訂單（可篩選狀態） | `mms_order_record` |
| `confirm_quote(quote_no)` | 用戶確認報價單（觸發 `confirm_time`） | `mms_order_record` |
| `cancel_order(order_no, reason)` | 取消訂單 | `mms_order_record.cancel_reason` |

---

### MCP Server 3：`vendor-backend-mcp`（廠商後台，B 端）

廠商端後台管理，含 AI 輔助回覆功能。

| Tool | 功能 | 對應資料 |
| --- | --- | --- |
| `list_pending_inquiries(vendor_id)` | 查看待處理諮詢單 | `pms_form_feedback` |
| `update_order_status(order_no, status, note)` | 更新訂單狀態（確認/完工/取消） | `mms_order_record.order_status` |
| `create_quote(order_no, items[])` | 建立報價單（含材料費 + 施工費） | `mms_order_record.order_items` |
| `generate_reply_draft(inquiry_id)` | AI 生成客戶回覆草稿（接 LLM）⭐ | `pms_form_feedback` 內容 |
| `get_service_analytics(vendor_id, date_range)` | 訂單量/完成率/金額分析 | `mms_order_record` 聚合 |

### 開發優先順序

```text
Phase 1（H1–H10，必做）：
  ✅ life-services-mcp  → list_services, search_services, list_districts
  ✅ order-management-mcp  → submit_inquiry, create_order, get_order_status, list_user_orders, confirm_quote

Phase 2（H11–H22，加分）：
  ⭕ vendor-backend-mcp  → list_pending_inquiries, update_order_status, create_quote, generate_reply_draft
```

### 關鍵設計注意事項

1. **個資處理**：所有涉及用戶身份的 Tool 一律用 `*_hash` 欄位識別，不傳明文
2. **`order_items` 是 JSON string**：在 Tool 內部 parse，不直接暴露給 LLM
3. **流程差異**：清潔/修繕先走諮詢單再轉訂單（`order_type: 01`）；餐廳訂位直接建訂單（`order_type: 02`），需分開處理
4. **`generate_reply_draft` 是亮點**：廠商後台讓 AI 幫寫回覆，Demo 時優先展示

## 技術架構

```text
┌─────────────────────────────────────────────┐
│           C 端：Web Chat UI                  │
│    (Text / Voice → 自然語言輸入)              │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│         LLM Agent（AWS Bedrock）             │
│   Claude 3.7 Sonnet / Nova Pro              │
│   - Intent 辨識                             │
│   - 多步驟 Tool 呼叫規劃                     │
│   - 對話記憶（Session Context）              │
└──────────────────┬──────────────────────────┘
                   │ MCP Protocol
┌──────────────────▼──────────────────────────┐
│         MCP Server（我們開發）               │
│  ┌─────────────────────────────────────┐    │
│  │ Tool: query_services()              │    │
│  │ Tool: create_order(service, ...)    │    │
│  │ Tool: get_order_status(order_no)    │    │
│  │ Tool: submit_inquiry(form_data)     │    │
│  │ Tool: confirm_quote(quote_no)       │    │
│  │ Tool: search_restaurants(...)       │    │
│  └─────────────────────────────────────┘    │
└──────────────────┬──────────────────────────┘
                   │ REST API
┌──────────────────▼──────────────────────────┐
│     統一資訊後端（Lumine one / PIC）         │
│   mms_order_record / pms_form_feedback      │
│   cms_homepage_service / sys_county         │
└─────────────────────────────────────────────┘
```

**技術選型**：

| 元件 | 選擇 | 理由 |
| --- | --- | --- |
| LLM | AWS Bedrock Claude 3.7 Sonnet | 符合比賽規定；中文理解強 |
| Agent Framework | AWS Strands Agents 或 LangGraph | 原生支援 Tool Use + MCP |
| MCP Server | Python（FastMCP） | 快速實作；官方有參考範例 |
| 前端 | Next.js + Vercel AI SDK | 快速建立 Chat UI |
| 開發輔助 | Kiro（AWS AI IDE） | 評分 +5% |

# 2026-07-18 方向更新：智慧社區 AI 助理

> 本節為工作坊後的最新規劃，與上方原始構想衝突時以本節為準。

## 官方最新說明（工作坊後補充）

- 以「**使用者**」的角度開發智慧管家
- 整合日常所需（**食衣住行育樂**）
- 目的：**方便、自動**
- **自然對話**，以引導式／任務式引導使用者完成任務
- 可預設背景：**樂齡、家庭、社區**（三選一或組合）
- **PPT 要說明情境 + 使用者**（persona 必備）
- **諮詢單**：問卷形式、**彈性題組設計**，使用者透過欄位填寫完成服務預約；題目可自行延伸
- 資料可自行擴充（合理即可）；**廠商 API 不提供，需自行模擬**

## 主題定位

> **智慧社區 AI 助理**（LINE 上的社區生活管家，對標官方 Lumine one 智能管家示範）

一個社區 = 一個 LINE 官方帳號。住戶用自然對話完成生活大小事；管委會／物業在後台開團、協調廠商；服務廠商接單報價。三個角色剛好一對一對應命題指定的三種角色：

| 我們的角色 | 對應命題角色 | 主要功能 |
| --- | --- | --- |
| 住戶（用戶） | (i) 消費者 C 端 | LINE 對話完成預約、購買、查詢；語音輸入 |
| 社區管理者（管委會／物業） | (iii) 設計後台 | 團購開團／結單、公設時段管理、推播設計、廠商協調 |
| 服務廠商 | (ii) 合作服務廠商 | 接諮詢單、開報價單、更新服務進度 |

**預設背景**：主打「社區」，並以「樂齡住戶」作為語音互動的重點 persona（一個場景同時吃到兩個官方預設背景）。

## 諮詢單 = 引導式對話的核心引擎（官方重點）

官方特別強調「彈性題組」，這正好可以做成整個系統的招牌設計：

1. 題組定義沿用官方 schema（`pms_form` / `pms_form_topic` / `pms_form_feedback`）
2. Agent **動態讀取題組定義**，逐題引導對話（＝官方要的「引導式／任務式」）
   - 例：「冷氣清洗」→ 追問「分離式還是窗型？」「幾台？」「偏好時段？」
3. 支援條件跳題（選了 A 才問 B）
4. **所有延伸服務共用同一套題組引擎**：修繕單、團購跟團單、公設預約單、活動報名單全是「一份題組定義 + 同一個對話引擎」——這就是我們「統一 API 規格」口號的具體化，簡報上非常好講
5. 樂齡場景：同一份題組改用語音逐題問答完成

賽前先擬 3 份延伸題組草稿：修繕（官方既有）、團購跟團、公設預約。

## 架構調整（LINE 取代 Web Chat 作為 C 端入口）

```text
LINE 官方帳號（住戶）
   │ Messaging API webhook
API Gateway → Lambda（channel adapter，薄層）
   │
LLM Agent（AWS Bedrock，Strands Agents／LangGraph）── 對話記憶、題組引導、意圖分派
   │ MCP Protocol
MCP Servers（沿用上方三個 server 規劃，工具不變）
   │
模擬統一資訊 API + 自建 DB（以 raw_data 為 seed，擴充團購／活動／公設資料）

管理者後台／廠商後台：簡單 Web 頁（或 LIFF），共用同一組 MCP tool
```

原則：**Agent 核心與通路解耦**。LINE 只是薄薄的 adapter，保留 Web Chat 作為備援 demo（LINE webhook 掛掉時不至於全場沒東西展示）。MCP Server 仍是繳交要求，不因改用 LINE 而省略。

### LINE 整合風險（賽前必須 spike）

- 需要 LINE Developers 帳號 + Messaging API channel（免費）
- Webhook 需公開 HTTPS endpoint（API Gateway + Lambda 即可，或 ngrok 應急）
- 語音訊息：LINE 傳 m4a → 下載 → Amazon Transcribe → 文字進 Agent
- 富訊息（Flex Message）很適合呈現報價單／團購清單，但排版花時間，先做 2–3 個樣板就好

## 0. 文件結構說明

- **第 1–2 節**：命題還原與整體策略

## 1. 命題官方要求還原

命題文件明確要求三個模組：

1. **消費者端**：文字/語音描述需求 → AI 判斷服務類型 → 產生對應的彈性留資表單並送出
2. **服務廠商端後台**：查看消費者需求、諮詢單內容、聯繫資訊、案件狀態；可延伸案件分類、需求摘要、狀態管理、回覆紀錄、進度追蹤
3. **服務媒合邏輯**：依服務類型、地區、時段、預算、緊急程度、服務商可服務範圍或評分推薦

**關鍵事實**：「競賽開發任務」（非加分項）明確要求把 API 包裝成標準 MCP Server，供「Lumine one 等外部 Agent」調用。經查證，**LumineOne 是統一資訊自有的企業級 AI Agent 平台**。本次比賽的本質是做**可被統一資訊 Agent 生態系調用的服務基礎設施**，不只是一個管家 App。

評分：創意度 15% / 技術可行性 25% / 商業應用性 25% / 主題切合度 20% / 完成度 15%（+5% Kiro）。

---

## 2. 整體策略

命題文件把 to C 流程寫得很白話，**同質化風險極高**——多數隊伍會做出幾乎一樣的「聊天 → 表單 → 後台列表」。

我們的分層策略：

| 層 | 目的 | 對應評分 |
|---|---|---|
| 基本盤做滿做穩 | 官方規格一項不漏 | 主題切合度 20% + 完成度 15% |
| 差異化亮點 | 可感知的功能差異 | 創意度 15% |
| 核心差異化（架構與方法論層面） | 證明工程與商業成熟度 | 技術可行性 25% + 商業應用性 25% |

to C 與 to B 收斂到**同一組 MCP Server**，直接命中必做的競賽開發任務。

---

## 3. 基本盤（必做，先做穩）

### 3.1 消費者端：意圖分類 + 動態表單

- **多輪釐清機制**：首句資訊不足時（「水管有問題」），AI 反問一次補齊關鍵資訊（位置/嚴重度/緊急性）再產表單。「彈性表單」的真義是欄位動態組合，不是固定模板。
- **表單 schema 驅動**：對應資料集 `pms_form_topic` 的題型體系（簡答/單選/複選/地區選單/上傳圖片，含 `feature` 欄位中的驗證規則如 regex、字數限制）。AI 只負責「選擇組合哪些欄位」，表單渲染由 schema 引擎處理——穩定性高、可測試。
- **語音輸入**：命題明確提及語音互動。用 AWS Transcribe 轉文字後接同一套流程，Demo 至少展示一次完整語音路徑。

### 3.2 廠商端後台：官方建議的五項全做（成本都不高）

- **需求摘要**：LLM 將 `feedback_content` 長文自動摘要成一行重點——最低成本、最高感知價值。
- **狀態管理**：對應 `order_status` 狀態機，做成看板（Kanban）介面，拖動卡片即改狀態。
- **案件分類 / 回覆紀錄 / 進度追蹤**：分類自動掛標籤；紀錄與進度用 timeline 呈現。

### 3.3 媒合邏輯：透明的加權評分公式

```
推薦分數 = w1×地區符合度 + w2×時段符合度 + w3×預算符合度
         + w4×緊急程度加權 + w5×服務商評分 + w6×產能負載(進階層)
```

Demo 時直接展示「為什麼推薦這家」的分數拆解——可解釋的媒合，不是黑盒子。

## 4. 差異化亮點（一般延伸層）

### 4.1 To C：生活事件偵測 → 生活事件規劃器（Orchestration）

- 利用 `member_name_hash` / `member_phone_hash` 重建同一使用者跨服務、跨時間的行為軌跡（官方定位僅「去重」，我們升級為行為序列分析 key）。
- 時間窗口內出現特定服務組合（清潔＋寄件＋修繕）→ 推論生活事件（搬家）→ 主動建議「事件包」。
- **進階版（真正的 Agentic）**：不只建議，而是排出有時序依賴的任務鏈（舊居清潔 → 寄件 → 新居水電檢修），依序調用 MCP tools 送出多筆諮詢單。此為進階 Demo 橋段，非主流程。
- 延伸：同 hash 短期重複提交緊急修繕/健康類諮詢 → 自動 flag 給社區服務窗口（主動關懷機制，呼應社區題旨與社會價值）。
- 技術：規則式時間窗口 pattern matching 即可做 MVP；LLM 負責把 pattern 轉譯成自然語言建議。

### 4.2 To B：報價自動駕駛 + 產能感知媒合

- **報價自動駕駛**：修繕服務（`service_id=17`）有正式報價流程（`quote_no`、材料費/施工費子項）。新案件進來時比對歷史同類 `itemName` 的報價分布，自動草擬報價單，廠商確認或微調即可。解決「廠商回覆慢＝平台流失率高」的真實痛點。
- **產能感知媒合**：用 `order_status` 分布（卡在「12 待確認」的案件數）推論廠商負載，滿載自動分流給次優但有空的廠商——把媒合理解為雙邊市場均衡，不是排序。

### 4.3 案件語意去重/聚合（社區場景專屬）

同棟大樓多住戶回報同一件事（電梯故障、公設漏水）→ embedding 相似度比對近期同地區同類型諮詢單 → 自動合併為同一案件，避免重複派工。技術僅需 embedding + cosine similarity，CP 值極高，且**直接對應「社區服務」的獨特場景**。

### 4.4 信任分數迴圈

案件完成後，LLM 分析完工紀錄＋消費者回饋文字，生成信任分數微調值回饋進媒合權重。用 `complete_time`、`refund_reason` 等欄位作為異常訊號來源，讓評分成為由真實服務品質驅動的閉環。

### 4.5 高齡友善的具體機制（不是口號）

- 語音優先＋送出前**語音複誦內容讓長者確認**。
- 高金額服務（修繕）加入**家人協同確認**選項：表單多一個「通知家人」欄位，家人收連結可共同檢視。

---

## 5. 核心差異化（深度策略層——真正的護城河）

### 5.1 AI 表單設計師：自我擴充的服務市場

**資料洞察**：實際檢視 `pms_form_topic` 範例資料證實——此平台的表單**完全是資料驅動**的。題型、驗證規則（`feature` 欄位含 regex、字數上下限）、排序、必填，全是資料庫 rows，不是程式碼。

**推論**：AI 可以「寫出」新的表單定義。

**機制**：
1. 使用者提出平台現有 6 類服務之外的需求（如「寵物照顧」）→ 系統不回「查無此服務」，而是記錄**未滿足需求**
2. AI 依 `pms_form_topic` / `pms_topic_option` schema 規範，當場草擬新服務類型的表單定義（題目、題型、選項、驗證規則），進入**待營運審核**狀態
3. 累積的未滿足需求 → B 端「**需求缺口儀表板**」：哪個地區、哪類服務有需求無供給 → 直接成為統一資訊的**招商依據**

**價值**：平台從「固定 6 類服務的媒合網站」升級為「會自我長出新品類的市場」。從官方資料表的設計哲學長出來的創新，不是憑空想像。

### 5.2 雙向 MCP：Agent-to-Agent 媒合談判

**命題文件伏筆**：「若合作廠商提供 API，是否可將相關服務包裝成 MCP Server」——暗示**廠商端也可以有 Agent**。

**未來使用者視角的媒合終局**：不是「排序演算法選一家」，而是：

```
消費者 Agent 發出需求
  → 多個廠商 Agent 依各自產能/行事曆/定價策略回覆可服務時段與報價
    → 平台 Agent 仲裁最佳組合
```

**Demo 設計**：做 2–3 個模擬廠商 Agent（不同產能與定價個性）對同一案件出價，現場展示協商過程。不需真正的多方談判引擎，即可展示「五年後的媒合平台」而非「2015 年接案網站＋聊天機器人」。

### 5.3 PII 防火牆：LLM 永不接觸個資的架構

**資料洞察**：個資欄位全部 AES-256-GCM 加密＋hash 伴隨欄位——**這個設計本身就是題目的一部分**（統一資訊 1800 萬會員、公開強調資安）。

**架構原則**：
- LLM 全流程只接觸 hash 與非個資欄位
- 真實聯絡資訊由**確定性（非 LLM）服務層**在最後一哩注入：廠商確認接案後，後端才解密並直接渲染到廠商介面，**全程不進模型 context**
- 架構圖明確標示「個資零暴露邊界」

**價值**：企業導入 LLM 的最大阻力就是個資進模型。這一頁架構圖對統一資訊背景的評審的說服力，可能超過任何功能 Demo。成本極低——是架構紀律，不是額外功能。

### 5.4 量化評測（Eval Harness）：黑客松裡沒人給數字

**資料洞察**：`feedback_content`（真實諮詢語料）＋ `order_items.itemName`（「水管-水管不通」「插座-插座沒電」）構成天然標註語料：文字描述 → 正確服務分類。

**機制**：
- 建意圖分類評測集，對 Agent 跑準確率與混淆矩陣
- 簡報放：「意圖分類在 N 筆真實語料達 X% 準確率，錯誤案例分析如下」
- 附帶好處：prompt 修改後可回歸測試，開發過程更穩

**價值**：技術可行性是最大單項配分（25%），可驗證的數字是最直接的取分方式。幾乎沒有黑客松隊伍會做評測。

### 5.5 Agent 行為治理：草稿 → 確認 → 稽核

所有 Agent 寫入動作走三態：**draft（AI 草擬）→ confirm(人工確認）→ audit log（誰/哪個 Agent/哪個 tool/何時）**。

實作成本：一個狀態欄位＋一張 log 表。回答的是企業對 Agentic AI 最深的恐懼——「AI 亂做事怎麼辦」。與 5.3 合併，整體敘事成為「**企業敢用的 Agent 平台**」，與 LumineOne 的企業定位同頻。

## 6. 架構核心:共用 MCP Server

**設計原則**：MCP Server 不是「聊天機器人背後的工具」，而是**任何 Agent（消費者端、廠商端、LumineOne）都能呼叫的共用服務介面**。

初步 MCP Tools 規劃：

| Tool | 功能 | 對應 |
|---|---|---|
| `classify_intent` | 文字/語音 → 服務類型判斷 | 基本盤 3.1 |
| `submit_case` | 產生彈性表單並送出諮詢單（走 draft/confirm） | 基本盤 3.1 + 治理 5.5 |
| `find_balanced_vendor` | 地區/時段/預算/緊急度/產能媒合 | 基本盤 3.3 + 亮點 4.2 |
| `draft_quote` | 依歷史資料草擬報價 | 亮點 4.2 |
| `get_case_status` | 案件進度查詢 | 基本盤 3.2 |
| `merge_duplicate_cases` | 語意去重聚合 | 亮點 4.3 |
| `detect_life_event` | 行為序列 → 生活事件推論 | 亮點 4.1 |
| `draft_form_schema` | 未滿足需求 → 草擬新表單定義 | 核心 5.1 |

**Demo 亮點**：做一個簡化的「LumineOne 模擬 Agent」下自然語言指令（「列出大同區超過 24 小時未回覆的修繕案件並草擬報價」），現場調用我們的 MCP Server 完成——證明我們做的是 Agent 基礎設施，不是聊天體驗。

## 8. 可行性與風險總覽（誠實版）

| 項目 | 風險 | 說明 |
|---|---|---|
| 意圖分類＋動態表單 | 低 | LLM + few-shot + schema 引擎，必做基本盤 |
| 廠商後台五項 | 低 | 標準 CRUD＋LLM 摘要 |
| MCP Server 包裝 | 中 | 需研讀官方 Reference Servers 熟悉規範 |
| 語意去重聚合 | 低中 | embedding + cosine similarity，需造同社區重複案例測試資料 |
| 報價自動駕駛 | 中 | 需先驗證範例資料中修繕樣本數是否足撐統計；不足則自造資料補強 |
| 生活事件偵測/規劃器 | 中高 | 2,041 筆資料中密集行為序列稀少，**必須提前自造資料**；誠實定位為「輔助建議」 |
| AI 表單設計師 | 中 | schema 生成本身可控（有明確格式規範），重點是審核流程 UI 要簡潔 |
| A2A 媒合談判 | 中高 | 模擬廠商 Agent 個性化出價需要額外開發，控制在 2–3 個簡化 Agent |
| PII 防火牆 | 低 | 架構紀律而非新功能，成本極低、說服力高 |
| Eval Harness | 低中 | 語料標註對應需先驗證品質；一旦建好持續受益 |
| Agent 治理三態 | 低 | 一個狀態欄位＋log 表 |

**共通風險**：多個亮點依賴「密度足夠的展示資料」。官方明文允許「根據格式自行生成數據資料」——**自造資料生成器應列為第一週開發項目**，甚至可包裝成交付物之一（市場模擬器）。

## 9. 評分權重對應

- **創意度 15%**：AI 表單設計師（5.1）、A2A 談判（5.2）、生活事件規劃器（4.1）
- **技術可行性 25%**：MCP Server 可被外部 Agent 實際調用的現場展示（6）＋ Eval 數字（5.4）
- **商業應用性 25%**：需求缺口儀表板＝招商依據（5.1）、報價自動駕駛解決流失痛點（4.2）、PII 防火牆＋治理＝企業可導入（5.3/5.5）
- **主題切合度 20%**：基本盤三模組全數做滿（3），語音互動、高齡友善（4.5）皆有對應
- **完成度 15%**：MVP 先鎖定基本盤＋MCP 基礎 tools，亮點依序疊加，不為亮點犧牲基本盤
