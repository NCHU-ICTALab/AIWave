# AIWave v4 初步提案構想（2026-08-01）

> 用途：業師交流、決賽簡報與五分鐘 Demo 的共同提案基線
> 狀態：產品與展示方向已確認；尚未完成的功能不得因寫入本文而對外宣稱已實作
> 詳細規格：[主動生活管家](../specs/16-proactive-life-butler-and-commercial-loop.md)／[自然對話 Agent](../specs/17-conversational-agent-session-and-llm-wiki.md)
> 展示原則：Demo-first，但所有示意資料、正式方案與待驗證合作必須分開

## 0. 一頁版

- **命題**：統一資訊「AI 生活管家：智慧社區服務需求理解與媒合平台」
- **提案名稱**：AIWave — 從生活情境到履約完成的 AI 生活管家
- **一句話**：AIWave 會理解會員的生活目標、在取得同意後編排跨服務任務，並追蹤 Provider 完成履約。
- **北極星指標**：生活任務完成率。
- **主商業假設（Demo 投影；正式條件待驗證）**：消費者免費；競賽版只在履約完成後顯示 Provider 成功服務費投影；正式收費、活動贊助與合作條件須經 Provider／品牌／命題方確認。
- **三個核心差異**：
  1. **可靠的生活服務底座**：服務、點數、訂單、通知、行事曆與 Provider 共用同一份狀態。
  2. **自然但可控的 Agent**：LLM 主導多輪理解、規劃與解釋；確定性平台掌管價格、時段、權限、授權與交易。
  3. **從情境主動走向執行**：生活提醒與可信指南可轉成準備清單、在地服務及可追蹤任務，而不是停在內容或推薦。

## 1. 痛點與產品答案

**[合理推導，待訪談驗證]** 一位會員想完成「爸媽週六要來，家裡需要清潔、燈要修、晚餐要訂」時，往往需要開多個 App、重填資料、自己對齊價格與時段，送出後還要分別追蹤。這是目前的產品假設，不代表命題方或會員研究已正式確認。

AIWave v4 的目標是提供同一條閉環：

```text
基礎服務探索與手動預約
→ 自然語言理解生活目標
→ 可編輯的跨服務任務包
→ 一次有界授權
→ Provider 逐項履約
→ 訂單、通知、行事曆同步
→ 生活成果與完成後商業事件
```

v4 再加入主動入口：

```text
生活情境事件
→ 有原因與來源的關懷卡
→ 情境式生活指南
→ 準備清單與「幫我準備」
→ 在地商品／服務與 OPENPOINT Demo 試算
```

主動入口沿用同一個 TaskDraft、Catalog、ExecutionGrant 與履約核心，不建立第二套交易流程。

## 2. 先基礎、後創新

**[目標 Demo 能力，待實作／待驗收]** 以下是決賽預計呈現的能力，不是目前完成清單。各項只有在程式、測試與 [五分鐘 runbook](../testing/v4-five-minute-demo-runbook.md) 實測通過後，才能改標為已有能力或對外宣稱已完成。

### 2.1 基礎功能

評審先看到 AIWave 是完整平台，而非聊天介面：

- 會員生活總覽：點數、近期行程、待辦與通知。
- 服務探索：Provider、Offering、真實 Demo 時段及服務範圍。
- 手動預約：表單、價格、點數折抵、確認與付款模擬。
- 履約追蹤：訂單、通知、行事曆與 Provider 工作台共用 `StatusEvent`。
- 產品 FAQ：AI 回答「怎麼使用點數／取消預約」，附來源並直接導向功能。

### 2.2 創新功能

- 自然多輪 Agent：能聊天、詢問、探索、規劃、修正、反悔與執行，不把每句話強迫變成訂單。
- Conversation Session：新對話、歷史、重開、重命名與封存；新聊天不被舊內容卡住。
- 可編輯任務包：逐項修改、刪除、暫緩，最後一次授權。
- 時間可達生活圈：以會場、社區、住家或目前位置為起點，顯示步行／機車 N 分鐘內可前往的服務。
- 情境式生活指南：將有來源的生活內容轉成清單、Catalog 需求及可執行任務。
- Steam 式成就解鎖：任務完成瞬間的愉悅微互動，不發點、不做 RPG。

## 5. 自然對話 Agent

目前問題不是模型不夠好，而是模型被限制成單句 JSON 抽取器，正常回覆與釐清多由模板產生。新版分成：

### 自然對話層

- 取得目前 Session 歷史、任務狀態、capability descriptions 與必要 Wiki 內容。
- 判斷本輪是聊天、產品求助、生活詢問、探索、規劃、執行或暫停。
- 自然承接「第二個」「改下午」「先不要」「只是問問」。
- 產生自然訊息、task patches 與 proposed actions。

### 確定性行動層

- 檢查 capability、Provider、時段、庫存、價格、點數、權限與冪等。
- 低風險查詢可直接做；外部影響操作必須有 `ExecutionGrant`。
- 將工具結果交回 LLM 生成 grounded 回覆。
- 方案、金額、日期、點數與狀態以權威卡片顯示。

驗收不逐字比對文案，而是測同義改寫、上下文、修正／反悔、非交易對話、Session 隔離及零未授權交易。

## 6. LLM Wiki 與情境式生活指南

競賽版文件量少，使用兩個分離的小語料域並把已發布內容全量放入 LLM context，不先建 RAG／Embedding／向量資料庫：

- **產品說明 Wiki**：只含目前版本真的可用的操作、限制與導覽。
- **生活指南 Wiki**：有來源、適用地區、步驟及準備項目，可在會員同意後連到 Catalog。

主生活指南是中元普渡準備；颱風與搬家／入厝列為後續。第三方內容只作產品形態參考，沒有授權不得擷取或改寫文章。

LLM 產生通用準備需求；SKU、價格、庫存、門市與點數由 Catalog／Provider 決定。推播先提供生活價值，會員開啟並點「幫我準備」後才呈現商品與服務。

## 8. AWS 規劃

```text
使用者
→ CloudFront／S3
→ ALB
→ ECS Fargate
   ├─ Platform／Web API
   │  ├─ Agent application service
   │  ├─ Bedrock 或可替換 LLM Client
   │  ├─ Aurora PostgreSQL
   │  ├─ ElastiCache（Session／短期狀態）
   │  ├─ Amazon Location adapter（正式 isoline，可用性待驗證）
   │  ├─ Secrets Manager／SSM
   │  └─ CloudWatch
   └─ MCP Gateway（無狀態）
      └─ 只呼叫 Platform API，不直連資料庫或狀態儲存
```

開發期沿用 OpenAI-compatible LLM 與 SQLite；外部相依放在 Protocol 後方。競賽環境權限不足時，Demo 使用固定 GeoJSON、fake upstream 及可重置 seed，不把 fallback 說成正式即時服務。

## 9. 商業閉環

主報告只說三件事：

1. 會員端目標維持免費使用 AI 生活管家。
2. 競賽版只在履約完成後顯示 Demo 成功服務費投影；正式版才假設 Provider 為已釐清需求、時段與預算的訂單支付成功服務費。
3. OPENPOINT 活動回饋未來可由品牌、Provider 或平台贊助；競賽版是明確標示的模擬。

正式收費是否成立、費率、Provider 合約、活動預算、品牌贊助、會計與退款條件都待官方或訪談驗證。會員端不顯示抽成；Provider／平台端在完成後顯示成交金額、Demo 成功服務費、示意贊助回饋及預估淨額。

- 未經授權交易次數：目標 0。

## 11. 誠實邊界

- `已有系統能力`、`待實作功能`、`Demo／示意資料`、`合理推導` 與`待官方或訪談驗證`分開標示。
- fake upstream、固定 GeoJSON、Demo points、費率與贊助不等於正式合作。
- 不複製未授權第三方生活內容，不由 LLM 捏造民俗或專業事實。
- 不做背景定位、恐懼式推播、秘密購物車或未經同意的交易。
- 不把成就提示包裝成核心商業價值。

## 12. 交流 Q&A

| 問題 | 回答要點 |
| --- | --- |
| 跟 ChatGPT 包殼差在哪？ | LLM 參與多輪理解、工具規劃與 grounded 解釋；平台以真 Catalog、TaskDraft、Grant、Provider 與 StatusEvent 完成副作用 |
| 為什麼不讓 LLM 全自動？ | 自然語言可以自由；金額、權限、庫存、狀態與交易不能猜，外部影響必須授權 |
