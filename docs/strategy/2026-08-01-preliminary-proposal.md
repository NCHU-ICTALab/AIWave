## 0. 提案大綱（一頁版，可直接貼進繳交表單）

- **隊名**：（填入）
- **成員**：（填入姓名／系級／分工）
- **命題**：統一資訊「AI 生活管家：智慧社區服務需求理解與媒合平台」
- **提案名稱**：AIWave — 個人目標驅動的 AI 生活任務編排平台
- **一句話**：會員只需說出生活目標，AI 就能跨服務、跨廠商、跨點數完成
  理解、拆解、比較、確認、派單與追蹤。
- **三個招牌能力**：
  1. 生活目標編排 — 自然語言多意圖拆解成有順序、可追蹤的任務
  2. 跨服務最佳方案 — 價格、點數、時段由規則試算，AI 負責理解與解釋
  3. 確認後執行到底 — 高影響操作先確認授權，執行後持續追蹤到履約完成
- **關鍵差異**：不是聊天機器人、不是服務型錄——AI 的產出是「被執行完的任務」，
  且金額、時間、權限、狀態一律由確定性規則守門，LLM 不碰錢。

## 1. 提案與命題之連結

### 痛點開場（先講人，再講技術）

一位會員想完成「爸媽週六要來，浴室燈壞了、冷氣也該洗了」這件事，今天要：

- 開 3～4 個 App 或 LINE 群組分頭詢價
- 每一家重填一次姓名、地址、時段等重複資料
- 自己比較價格與時段，沒有工具幫忙對齊
- 送出之後沒有人追蹤進度，出問題只能自己打電話

命題要的「服務需求理解與媒合」，失敗成本就藏在這四步裡：**流失的不是需求，
是把需求走完的耐心。**

### 一條可記住的工作流（回應命題的核心答案）

```
理解目標 → 拆解任務 → 試算與媒合 → 一次確認 → 履約追蹤
```

- **理解**：自然語言、多意圖、口語地名與相對日期（「明天下午」「北區」）。
- **拆解**：一句話拆成多個相依任務（修繕＋清洗＋點數試算），只追問會影響
  執行的缺漏資料。
- **媒合**：不做黑箱媒合——從核准廠商、方案、真實可用時段中比較並說明理由，
  最終選擇權在使用者。
- **確認**：使用者一次預覽所有任務，核准後才建單；點數折抵金額可重算驗證。
- **追蹤**：廠商回覆、狀態變化即時同步到會員的訂單、通知與行事曆。

### 與相鄰平台的邊界（避免「重做別人產品」的質疑）

| 平台 | 它的核心 | AIWave 的關係 |
| --- | --- | --- |
| OPENPOINT | 帳號、點數、優惠、品牌服務入口 | 使用其生態資產，不重做點數平台 |
| 社區管理平台 | 管理費、公告、包裹、門禁 | 未來作為 connector 介接，不重做社區營運 |
| 單一服務商 App | 單一品牌的預約與履約 | 編排成跨廠商任務的執行單元 |
| **AIWave** | **個人目標驅動的跨服務任務編排** | 位於上述三者之上的編排層 |

## 2. 企業數據及資料應用

初步探勘官方提供的資料後，我們的設計讓企業資產進入**核心決策**，不是裝飾：

### 2.1 官方表單 schema 直接作為留資表單引擎的基礎

- 沿用 `pms_form / pms_form_group / pms_form_topic / pms_topic_option` 四表結構，
  題型嚴格採用官方 `type` 代碼 1–10，不自創題型。
- 跳題邏輯規劃存放在官方既有的 JSONB `feature` 欄位——**官方資料表零修改**，
  所有新功能一律外掛擴充表。
- 效益：未來平台上的既有表單可直接載入，AI 動態問答與人工填表共用同一份定義。

### 2.2 官方訂單資料驅動個人化

- `mms_order_record` 樣本（99 筆、10 個帳號）作為行為軌跡與消費摘要的資料來源，
  儀表板數字全部由真實樣本計算，不硬編碼。
- 樣本中的 `member_*_hash` 欄位跨帳號重複——初步驗證可將 10 個通路帳號歸併為
  8 個真實身分。這就是命題方生態的「行為指紋」價值：**跨通路識別是資料裡
  真實存在的能力，不是我們虛構的**。
- 推薦採可解釋混合式：確定性規則決定「推什麼、為什麼」，並附上指向真實
  `record_id` 的證據；LLM 只負責自然語言解釋。修繕、訂位等事件驅動型服務
  刻意排除在「回訪型推薦」外，避免推出「該修水管了」這種荒謬建議。

### 2.3 官方地區與服務主檔

- 口語地名（「台中北區」，含臺／台正規化）解析為官方 `county_code` /
  `district_code`，媒合時用官方行政區編碼對齊廠商服務範圍。
- 官方服務主檔對應到平台服務目錄；`order_type=07`（商城／團購）等實際資料
  中的慣例照實沿用。

### 2.4 資料治理承諾

- Demo 人物一律虛構；不把任何真實個資帶入競賽環境（符合官方 13 類禁令）。
- 展示資料、推論資料、真實樣本資料在 UI 上分別標示來源，不混用。

## 3. AWS 雲端技術架構（規劃）

> 設計原則：評分表寫「使用體驗良好流暢」，所以**每一個選型都對應一段被消除的等待**。

```
使用者 ──> CloudFront + S3（前端靜態，邊緣快取）
       ──> ALB ──> ECS Fargate 常駐（API + MCP Gateway，min 2 task 跨 AZ）
                      ├─> Amazon Bedrock（Claude，同區推論）
                      ├─> Aurora Serverless v2（PostgreSQL 相容，min 2 ACU）
                      ├─> ElastiCache for Redis（對話 session）
                      ├─> Secrets Manager（憑證）
                      └─> CloudWatch(日誌／指標／告警)
```

| 選型 | 不選的方案 | 理由（消除哪段等待） |
| --- | --- | --- |
| ECS Fargate 常駐 | Lambda | 冷啟動會落在評審按下第一個按鈕的那一刻 |
| Aurora min 2 ACU | 0.5 ACU 起步 | 第一個查詢不必等暖機 |
| ElastiCache | 行程內 session | 多 task 下第二句話打到另一台仍在同一個工作階段 |
| Bedrock 同區 | 地端模型 | 省掉跨境往返；AWS 命題用 AWS 托管 AI 是自然答案 |
| CloudFront + OAC | S3 公開網站 | 官方規範禁止 S3 公開，且邊緣快取更快 |

### 呼應官方競賽環境規範（展現我們讀過公告）

- **Bedrock 全帳號 ≤1 RPS**：LLM 呼叫層內建序列化佇列＋退避重試，
  「一則使用者訊息＝一次理解呼叫」；多人同時操作時 UI 顯示排隊回饋而非逾時。
- **GPU 配額為 0**：不做自架模型或大規模訓練，雲端 AI 一律走 Bedrock。
- **安全**：SG 僅開 80/443（SSH 走 SSM Session Manager）、憑證進 Secrets
  Manager、容器內不落地 `.env`、S3 Block Public Access。
- **區域**：`us-east-1`，與指定區域一致。

### 可移植性（地端先行的風險控管）

所有外部相依（LLM、資料庫、session、廠商 API）都藏在 Protocol 介面之後：
開發期以地端 OpenAI 相容端點與 SQLite 驗證邏輯，上雲只換介面實作，
呼叫端一行不改。這讓我們能把比賽時間花在產品，而不是雲端除錯。

## 4. 生成式 AI 技術應用

核心原則：**LLM 負責規劃，規則負責執行。**

| 層 | 由誰決定 | 說明 |
| --- | --- | --- |
| 理解與拆解 | LLM | 多意圖辨識、口語→結構化答案、任務相依排序 |
| 追問策略 | 模板＋表單引擎 | 問題是確定性的（可測試）；只有「解讀使用者回答」交給 LLM |
| 價格／點數／時段 | 確定性規則 | 試算器可重算驗證，LLM 不產生任何金額 |
| 時間解析 | TimeResolver | 「明天」「下週三」以 Asia/Taipei 伺服器時間解析，確認畫面回顯絕對日期 |
| 推薦 | 規則決定＋LLM 解釋 | 每則推薦附真實訂單證據，可解釋、可重算 |
| 執行授權 | ExecutionGrant | 交易類操作需使用者核准範圍（廠商、時間、預算上限、期限），超出即停下再確認 |

### 安全邊界（信任機制可被展示）

- 工具的 JSON Schema 中**沒有 `account_id` 參數**——身分由伺服器端注入，
  LLM 或外部 Agent 無法要求讀別人的資料。
- 寫入動作一律先確認；執行端不信任前端回傳的步驟，會重新驗證。
- LLM／解析失敗一律降級為「聽不懂，請再說一次」，永不讓對話崩潰。
- 不展示模型原始思考鏈；串流顯示「理解需求→查詢服務→準備方案」等可驗證進度。

### MCP：讓外部 AI 也能操作平台

規劃將平台能力以 MCP（Streamable HTTP Gateway）開放給外部 AI 助理，
與 Web、站內 Agent 共用同一套能力、權限與確認規則——同一個授權模型，
三種操作入口。

### 決賽 Hero Demo 腳本（口頭說明用）

> 「爸媽週六要來，浴室燈壞了、冷氣也很久沒洗，幫我安排一下，OPENPOINT 能省就省。」

1. AI 解析為水電修繕、冷氣清洗、點數試算三個相依任務
2. 自動套用會員地址、時段偏好；缺的資料以聊天框上方按鈕補齊

5. 廠商更新狀態，會員在 AI 與訂單頁看到同一份進度；
   現場注入一次逾時，展示降級、重試與稽核（信任機制的實地證明）

- 點數節省金額，且每個數字可重算
- 上游逾時時是否仍能走完可用的替代流程

## 6. 商業閉環（交流時被問到再展開)

```
會員更容易完成任務 → 更多結構化需求與轉換
→ 群組聚合需求、降低廠商獲客成本 → 更多廠商以標準契約接入
→ 方案更完整、點數使用率提高 → 未滿足需求成為招募廠商的情報
```

廠商接入規劃三種模式（自建 API／Adapter 轉接／無 API 直接用工作台），
降低長尾服務商的進入門檻——媒合平台的供給面就是這樣長出來的。

## 7. 交流 Q&A 預備

| 可能的提問 | 回答要點 |
| --- | --- |
| 跟 ChatGPT 包個殼差在哪？ | LLM 只做理解與規劃；金額、時段、權限、狀態全由確定性規則裁決，且 AI 的產出是被執行完的任務，不是一段文字 |
| 媒合怎麼避免亂配？ | 不做黑箱媒合：從核准廠商與真實時段中比較並說明理由，使用者保有最終選擇權 |
| 企業資料用在哪？ | 官方表單 schema 直接當表單引擎、官方訂單算行為軌跡與推薦證據、member_hash 跨通路歸併身分（10 帳號→8 身分是資料中真實可驗證的） |
| 幻覺與安全？ | 工具參數層面就拿不到別人的身分；寫入必經確認；解析失敗降級不崩潰；金額不由 LLM 產生 |
| Bedrock 1 RPS 撐得住 Demo？ | 序列化佇列＋退避重試＋排隊 UI；一則訊息一次呼叫的預算設計 |
| 做得完嗎？ | 介面隔離讓地端與雲端實作可以並行；P0 先做住（修繕／清潔）、食（訂位）、預（購物）的完整閉環，其餘場景以共用核心擴充 |
