圖 2 · 主線

一句話到一筆訂單

Demo 的主幹，依序發生。橘色是 LLM 參與的回合，綠色是授權閘門——中間這道 ExecutionGrant 就是「AI 不會自己亂下單」的證據。

  1. 1住戶 → Web

    「陳伯伯下週要回診，順便叫個車」

  2. 2Web → Agent

    POST /agent/messagesSession 持久化於 SQLite，可重開、重命名、封存

  3. 3Agent → LLM

    拆子任務、抽服務關鍵詞與日期片語LLM 只回語意草案，不含任何事實

  4. 4Agent → 註冊表・目錄

    服務是否存在？有沒有時段？價格多少？模糊需求（例如「洗衣服」）回釐清選項，不硬答也不回「沒有服務」

  5. 5目錄 → Agent

    真實 offering、slot 與報價服務有無、日期、價格全由規則裁決，LLM 說了不算

  6. 6Agent → TaskDraft

    預填草稿，逐欄標記來源（AI 填的還是使用者填的）

  7. 7Agent → 住戶

    提案卡：模板理由 + evidence理由是模板文字，永遠可驗證，不是模型自由發揮

  8. 8住戶 → ExecutionGrant

    確認範圍：服務商、時間範圍、預算／點數上限、到期時間

  9. 9送單 → Grant 檢核

    consume 涵蓋該筆交易的已核准授權超範圍或過期直接擋下（ADR-0008）

  10. 10平台 → Provider

    connector 現場驗證後建單探索讀投影不依賴上游存活，但下單一定即時驗證

  11. 11平台 → 住戶

    StatusEvent 時間軸、通知、行事曆事件同時到位

任何一步的 LLM 解析失敗都重試一次，再失敗就誠實降級為追問——不會崩潰，也不會憑空生出服務。測試：tests/test_agent_m8.py、tests/test_agent_guardrails.py

職責邊界：LLM 規劃，規則執行

這是評審最常追問的一題。若只留一張投影片，留這張。

LLM 只做這三件事

  • 把一句話拆成子任務
  • 抽服務關鍵詞與日期片語
  • 抽表單欄位值

全部由確定性模組裁決

  • 服務是否存在、時段是否可訂
  • 日期解析、價格與點數折抵
  • 授權範圍與所有副作用
設計選擇為什麼這樣切依據
官方表結構零修改新功能一律外掛擴充表，跳題邏輯放官方 JSONB 欄位，交付方導入不需改 DDLADR-0002
個人／家庭／社區同一機制共用 owner_scope 加 grp／group_member，不是三套子系統；同一檔團購住戶與管委會看到不同視角，資料只有一份ADR-0003
外部依賴都在 Protocol 後面LLM 與持久化可換成 Bedrock 與 RDS，呼叫端一行不動ADR-0004
ExecutionGrant 有界授權產生交易前必須有涵蓋該筆的已核准授權，超範圍或過期直接擋下ADR-0008
目錄投影與上游分離探索讀投影，不依賴上游存活；但下單前仍由 connector 現場驗證ADR-0007
推薦可解釋規則決定推什麼與為什麼並附 evidence，LLM 不參與評分ADR-0011 / 0017
