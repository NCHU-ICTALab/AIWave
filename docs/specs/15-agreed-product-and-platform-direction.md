# AIWave 產品與平台定案基線

> 狀態：現行且具最高優先級  
> 定案日期：2026-07-30  
> 適用範圍：產品、Web、後端、Agent、MCP、廠商 API、fake server、測試與部署  
> 若其他文件與本文件衝突，以本文件為準；尚未完成的功能不因寫入本文件而視為已實作。

## 1. 產品定義

AIWave 是一個以個人會員為主體的生活服務作業系統。它把分散的服務、點數、行程、通知、群組與社區情境放入同一個可追蹤的任務流程，並讓使用者選擇手動操作或交由 Agent 協助。

AIWave 不是第二個 OPENPOINT、純聊天機器人、服務型錄、社區管理 App，也不是只有畫面的 mock demo。差異化在於：

1. 同一件生活目標可跨服務拆解、安排、確認、執行與追蹤。
2. 手動流程、Agent、MCP 與廠商後台操作的是同一份資料和狀態機。
3. Agent 能規劃與採取行動，但金額、權限、時間、服務存在性及訂單狀態由確定性規則守門。
4. 廠商即使沒有既有 API，也能透過公開契約、Adapter 或工作台加入生態。

## 2. 服務範圍與完成深度

官方生活場景是食、醫、住、行、預、樂；說明會另列外送、訂位、清潔、修繕、宅配、購物、影音、領藥，書面命題包含 App 叫車。類別可擴充，不把產品寫死為固定六格或八格。

### 2.1 閉環定義

一個服務只有同時具備以下內容，才能宣稱「完成閉環」：

1. 使用者能從服務頁手動開始，不必依賴 Agent。
2. 有真實可操作的選項、表單驗證與後端資料。
3. 依服務類型選擇店家、方案、資源／人員與真實可用時段。
4. 使用者確認後建立訂單、預約或諮詢單。
5. 合作方或 fake upstream 能收到並回覆。
6. 使用者端能看到由履約事件驅動的進度條、通知與行事曆變化。
7. 至少有一條可恢復的失敗路徑，且重新整理、上一頁與重試不會破壞狀態。
8. 同一能力能被 Agent 與 MCP 操作，且權限與確認規則一致。

### 2.2 優先順序

| 優先級 | 內容 | 目標 |
| --- | --- | --- |
| P0 | 住：清潔、修繕；食：訂位；預：購物／i 預購 | 各至少一個完整閉環；住做最深 |
| P1 | 行：叫車；樂：影音／娛樂；外送；宅配 | 以共用核心擴充成可執行閉環 |
| P2 | 醫：處方箋辨識＋藥局連結／領藥；語音 | 時程允許才做；未完成不得顯示可點入口或對外宣稱 |
| 延後 | LINE／Discord、正式 AWS 最終架構 | Web 完整且穩定後再做 |

真實廠商、服務欄位與參考表單由產品負責人提供後才定案。開發不得擅自用敵對品牌或杜撰奇怪名稱填滿正式 Demo。

## 3. 使用者、角色與工作空間

### 3.1 一個帳號，多個角色

`Account` 是登入身分；`RoleMembership` 表示帳號在某個工作空間中的權限。單一帳號可同時是：

- 一般會員
- 合作廠商人員
- 社區管理者
- 平台營運者

使用者必須明確切換 `Workspace`，不可因為登入過某角色而混用資料。Demo 快速登入則提供固定、彼此隔離的人物，方便測試不同視角。

### 3.2 三種資料範圍

- `personal`：個人訂單、點數、偏好、提醒與行程。
- `group`：使用者自行建立及命名的群組。系統不要求家庭／朋友／情侶等群組類型。
- `community`：真實社區組織，含住戶、管委會／管理者、公告、設施與社區服務，不是 Group 的一種。

社區不是註冊必填。會員可透過邀請、申請或管理者核准加入多個社區，並設定預設社區。社區管理權另行申請與人工審核；競賽版不假裝完成真實身分驗證。

## 4. 手動流程與 Agent 共用 TaskDraft

### 4.1 手動永遠可用

所有功能必須先有完整手動路徑。Agent 只負責理解、規劃、預填、比較、導覽與受控執行，不建立另一套隱藏流程。

使用者在每個環節都可脫離 Agent，直接修改表單。Agent 與手動 UI 共用 `TaskDraft`：

- Agent 從對話取得的內容自動預填到正式表單。
- 使用者修改後的值優先於 Agent 推測、會員資料與廠商預設。
- 來回切換不遺失對話、草稿、選項或驗證錯誤。
- 訂單成立後不直接改原始內容，改走改期、變更或取消流程。

桌面版採主要工作區＋Agent 側欄；手機可切成全頁 Agent。獨立 AI 頁與側欄必須共享同一段對話與草稿。

### 4.2 Agent 自主性與安全邊界

Agent 可以拆解目標、選工具、比較方案、重新規劃與解釋取捨，不限制成只能聊天。以下內容由確定性模組裁決：

- 現在時間與相對日期
- 服務、據點、方案與時段是否存在
- 金額、點數與退款
- 帳號、角色、scope 與 API scope
- 訂單狀態轉移、冪等與稽核

`TimeResolver` 以 `Asia/Taipei` 的伺服器目前時間解析「明天」「下週三」，並在確認畫面回顯絕對日期。`Service Registry` 保存服務同義詞、能力與必要欄位；「洗衣服」等模糊需求應釐清是到府家務或送洗，不能直接回答沒有服務。

低風險讀取與規劃可直接做。會產生交易或外部影響時，使用者核准有範圍與期限的 `ExecutionGrant`，內容至少包含服務商、時間範圍、預算／點數上限與到期時間。超出授權或條件改變時必須停下再確認。

串流介面顯示可驗證進度，例如「正在查詢可用時段」「已找到 3 個方案」「等待你確認」；不顯示模型原始思考鏈。

## 5. 服務選擇、預約與訂單

平台不把廠商當成黑箱媒合結果。正常預約流程是：

1. 選服務／方案。
2. 從核准清單選店家或據點。
3. 視服務需要選人員、車種、房型或其他資源。
4. 從廠商提供的可預約空檔選時段。
5. 檢查價格、點數、個資與取消規則後確認。

Agent 可以排序並說明 1–3 個建議，但最終選擇權在使用者。清潔／修繕等諮詢型服務可先送需求再由廠商提供報價或可服務時段；有明確庫存／時段的服務不可讓使用者填一個實際不存在的時間。

訂單進度使用電商熟悉的視覺時間軸，但狀態名稱依服務類型定義，例如：

- 訂位：已建立 → 店家確認 → 即將到店 → 已完成
- 修繕：需求送出 → 廠商回覆 → 已預約 → 服務中 → 已完成
- 購物／宅配：收到訂單 → 備貨 → 理貨 → 出貨 → 已送達

所有頁面的進度、數量與待辦必須來自同一份 `StatusEvent` 事件流。

## 6. 共用平台核心

各服務不是一張塞滿 nullable 欄位的萬用訂單。每個 domain flow 有自己的深層介面，底層共用：

- 身分、角色、scope 與稽核
- `TaskDraft`、確認與 `ExecutionGrant`
- 訂單／預約識別碼與 `StatusEvent`
- 點數、Demo 支付、退款與沖銷
- 通知中心與行事曆 projection
- ProviderConnector、錯誤復原與冪等

### 6.1 點數與支付

競賽版使用可重置、明確標示 Demo 的 OPENPOINT 情境帳本。所有頁面讀同一份餘額、取得、折抵、退款與到期紀錄。折扣試算由確定性計算器完成，Agent 只負責解釋與納入方案。

`DemoPaymentAdapter` 不蒐集真實卡號，但必須能展示成功、失敗、取消、退款與點數沖銷。

### 6.2 通知與行事曆

通知採持久化事件中心，支援已讀／未讀、深層連結、scope、安靜時段；外部推播之後再接。

AIWave 行事曆是訂單、生活任務、提醒、群組與社區事件的統一 projection，提供月／週／列表與來源篩選。可建立簡單的手動事件及週期事件；修改週期時要能選本次、未來或全部。廠商預約不可直接拖曳改時間，拖曳只會啟動正式改期流程。

### 6.3 推薦

推薦分為三種，UI 與資料來源不可混在一起：

- 任務型：完成當前目標需要的下一步或替代方案。
- 個人化：根據經同意的行為特徵與偏好。
- 推廣型：必須明確標示廣告／合作推薦。

「不感興趣」只影響單一個人化或推廣項目，提供復原，不可關閉整區推薦。任務型建議提供「修改條件」而不是不感興趣。

## 7. 合作廠商接入

### 7.1 三種模式

三種接入方式實作同一個 `ProviderConnector`：

1. 標準接入：廠商實作 AIWave 公開契約。
2. Adapter 接入：AIWave 將既有廠商 API 轉成內部契約。
3. 工作台接入：沒有 API 的廠商直接使用合作方後台。

廠商是據點、方案、人員／資源、可用時段、接單與履約狀態的權威來源；AIWave 是會員確認、跨場景任務、點數、通知與稽核的權威來源。

### 7.2 Partner API

「三支 API」視為三個能力群組，不硬塞成三個端點。OpenAPI 3.0 是唯一契約來源，Postman collection 由規格產生。最小表面預計為：

- `PUT /partner/v1/catalog`
- `PUT /partner/v1/availability`
- `GET /partner/v1/bookings`
- `PATCH /partner/v1/bookings/{booking_id}`
- `GET /partner/v1/snapshot`
- 選配：簽章 webhook

API key 必須雜湊保存、限制 partner 與 scopes；寫入端點必須支援 idempotency key。廠商申請、人工審核、發 key、測試與核准上線都要有可展示狀態。

### 7.3 獨立 fake server

fake server 是可獨立啟動的上游系統，不是前端 fixture。它必須：

- 實作同一份 OpenAPI 契約。
- 使用台灣中文 seed，品牌需通過核准 allowlist。
- 支援 reset、seed version、延遲、錯誤與狀態未知注入。
- 與每個測試者的 DemoWorkspace 協調重置，避免平台保存的遠端 ID 失效而持續 404。
- 讓 Fake 與 Real adapter 只由後端環境變數切換，瀏覽器不可選模式。

## 8. AIWave MCP

MCP 的產品定位是「讓遠端 AI 安裝／設定 AIWave MCP 後，能在授權範圍內操作整個系統」，不是專供站內聊天室使用，也不是廠商 API 的別名。

### 8.1 架構

- Python SDK 使用 `mcp==2.0.0`，以目前協議能力為準並保留較早協議版本相容性。
- 正式入口是遠端 Streamable HTTP MCP Gateway；本機保留 stdio 開發 proxy。
- MCP server 無狀態，只能透過 AIWave Platform API 操作，禁止直接連 DB、repository 或在行程內自行建 service container。
- MCP tool 與 Web 共用 capability、權限、schema、確認、冪等與稽核規則。
- Demo bearer key：會員 `aiwave`、合作方 `aiwave-partner`、社區管理 `aiwave-manager`、平台測試 `aiwave-admin`。
- `aiwave-admin` 只用於固定 Demo workspace／persona 的管理和切換，不等於無限制越權。
- 未來改用 OAuth／OIDC、動態 client registration 與細粒度 scopes；不把 Demo key 當正式資安設計。

長時間工作以 AIWave 的 domain task／order ID 追蹤，不依賴 Python SDK 尚未提供的 MCP Tasks extension。文件／處方箋先走 upload API 或 S3 取得 `document_id`，不把大型 base64 塞進 MCP payload。

## 9. Web 體驗與設計審批

### 9.1 資訊架構

公開首頁先說清楚產品價值，右上角提供傳統登入入口。登入頁包含帳號密碼與 Demo 快速登入。登入後會員主導覽固定為：

1. 首頁
2. 點數兌換
3. AI
4. 服務
5. 會員中心

首頁是資訊總覽，包含點數、消費、近期行程／待辦、推薦、廣告標示與常用功能；行事曆由首頁卡片進入，不新增第六個主頁籤。

### 9.2 設計流程

正式改寫 Vue 前，必須先交付並由產品負責人核准兩組 HTML 原型：

- 新的成熟消費者 Dashboard 方向。
- 參考 `C:\Users\alen9\Documents\NCHU\competition\aws summit taipei\code` 過往得獎前端的方向。

公開首頁也要先以 HTML 預覽核准。住戶端可親和但要像成熟產品；合作方與管理端可提高資訊密度。所有介面共用設計 token，符合 WCAG 2.2 AA：可見焦點、鍵盤操作、至少 44px 目標、文字對比、非僅靠顏色傳達、不以 hover 改變 layout、避免巢狀捲動，並驗證 390px 與 1440px。

## 10. DemoWorkspace 與重置

每位測試者使用隔離的 `DemoWorkspace`，包含帳號、訂單、點數、Agent 對話與草稿、行事曆、通知、群組及社區資料。一般使用者只能重置自己的 workspace；`aiwave-admin` 可重置固定 Demo personas 與 fake upstream。

重置必須是協調式操作：平台資料、fake server、seed version 與遠端 ID 一起回到相容版本。健康檢查要能指出 seed version 不一致，不能以無止盡 404 當正常輪詢。

## 11. 完成定義

任何可見功能都必須滿足：

- 有實際 handler 和後端資料，不是靜態 HTML 或無作用按鈕。
- 重新整理、上一頁與重新登入後狀態一致。
- 帳號、角色、workspace、partner 與 scope 隔離正確。
- 有成功與至少一條可恢復失敗路徑。
- 支援 reset，數字跨頁使用同一來源。
- 390px／1440px 與 WCAG 2.2 AA 基本驗證通過。
- 手動、Agent 與 MCP 對同一能力產生一致結果。
- domain、API、contract、Agent、MCP 與瀏覽器測試覆蓋主要閉環。

沒有符合以上條件的功能不得放在 Demo 主路徑，也不得用靜態假數字宣稱已完成。

## 12. 實作順序

1. 文件、領域模型與過時文件封存。
2. Account、RoleMembership、Workspace、Group、Community、DemoWorkspace。
3. 訂單／預約、StatusEvent、DemoPayment、點數、通知、行事曆共用核心。
4. OpenAPI、Partner API、ProviderConnector 與獨立 fake server。
5. 取得真實品牌及表單後，完成住、食、預手動閉環。
6. 以共用核心擴充行、樂、外送與宅配。
7. 交付公開首頁與登入後介面的 HTML 方向，核准後才改 Vue。
8. 把手動 Web 流程做到穩定、可測且一致。
9. 加入 Service Registry、TimeResolver、TaskDraft、ExecutionGrant 與 Agent。
10. 將現有 MCP 重構成 SDK v2 的遠端 Gateway。
11. 完成自動測試、瀏覽器驗收與 WCAG 檢查。
12. 視時程處理醫、語音；Web 完美後才評估 LINE 與正式 AWS。

## 13. Demo 主故事

公開首頁 → 會員登入與資訊總覽 → 手動建立一筆預約 → Agent 接收跨場景目標 → 使用者中途切回手動修改 → 核准 ExecutionGrant → 建立訂單 → 合作方工作台即時收到並確認 → 會員端的進度、通知、行事曆與點數同步更新 → 注入一次可恢復 timeout 並重試 → 外部 MCP client 讀取同一筆任務 → 展示 OpenAPI 與三種廠商接入模式。

其他閉環以服務總覽、測試證據與必要的短畫面證明，不在現場逐一點完。

## 14. 明確延後與待輸入

- LINE／Discord 整合：Web 完成後再討論。
- 商業模式與簡報話術：屬提案簡報工作，不作為本輪系統需求。
- 正式 AWS：先地端完成；Learner Lab 只做權限與可行性探索，之後使用產品負責人提供的完整環境。
- 真實廠商／品牌、服務欄位與參考表單：每一類實作前必須向產品負責人確認。
- 醫療與語音：P2，可在工期不足時不做，但 UI 與文件必須誠實反映。
