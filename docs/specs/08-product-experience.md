# 08・產品體驗：從「能 demo」到「能用」

> 建立日期：2026-07-26　狀態：**診斷與三項分岔均已定案**（見 §7），實作進行中
>
> 這份文件記錄一個轉向：我們前期一直在「為了 demo 而做」，導致一個初次到訪的使用者
> 不知道怎麼用、也不會想用。本文記下**當時發現了什麼**、**為什麼要轉向**、以及
> **產品化具體是什麼意思**，讓未來的我們（或新加入的人）不必重新推導一次。

## 1. 觸發這份文件的觀察

打開 `/` 會直接 redirect 到 `/app/today`，畫面顯示「已完成消費 NT$2,218」。

**一個從沒用過這個 app 的人，為什麼會有消費紀錄？**

這不是 bug，是心智模型的問題：我們一直在建「一個能展示所有功能的畫面集合」，而不是
「一個人會使用的產品」。功能是真的、資料是真的、測試是綠的——但沒有人能自己走進來用。

## 2. demo 化痕跡清單（可逐項核對）

| # | 痕跡 | 產品裡應該是什麼 |
| --- | --- | --- |
| 1 | `/` 直接進儀表板，沒有入口 | 落地頁：這是什麼、為什麼要用、怎麼開始 |
| 2 | 頂端下拉切換**四個工作區**（個人／社區／廠商／平台） | 真實使用者是住戶**或**廠商，不會是四個。這是給評審的開關 |
| 3 | 「重設」按鈕 | 產品裡不存在 |
| 4 | 沒有登入、沒有「我是誰」 | 沒有身分，就沒有「我的東西」 |
| 5 | **AI 躲在「問生活管家」抽屜裡** | 這是產品的核心價值，不該是側邊按鈕 |
| 6 | 找服務＝九張卡片目錄 | 使用者想的是「我家漏水」，不是「我要買『水電修繕』這個 SKU」 |
| 7 | 沒有零狀態設計 | 沒訂單時要教使用者怎麼開始，不是空白或塞假資料 |
| 8 | 社區／廠商／平台頁數字寫死（18 戶、99.2%、7 個連接器） | 由真實資料算，或明確標示為情境設定 |

**最核心的一條**：使用者打開 app 的第一個問題是「我現在該做什麼」，
而我們現在的答案是「請從六個導覽項目裡自己找」。

## 3. 為什麼這同時是比賽策略

產品化不是額外的理想主義，命題與評分表直接要求它：

- 命題原文：「評委以**讓用戶使用者的角度**去體驗」
- 評分標準：「完成度 15%：功能完整，**使用體驗良好流暢**」

**評審打開後不知道怎麼用，這一項直接扣分。** 所以「做成真產品」與「贏比賽」同向，
不需要在兩者之間取捨。

## 4. 產品原則（用來判斷取捨）

1. **每個畫面都要能回答「我現在該做什麼」**——主動作只有一個，其餘是次要入口。
2. **沒有資料時要教學，不要造假**——零狀態是設計對象，不是待填的空白。
3. **AI 是門面，不是功能之一**——差異化在「說一句話就有人接手」；主畫面若是型錄，
   我們就只是一個服務型錄網站。
4. **展示用的機制要嫁接在真實概念上**——切換角色＝切換登入身分，不是切換 demo 模式。
5. **畫面上的每個數字都要指得出來源**——延續 [ADR-0011 可解釋推薦](../adr/0011-explainable-hybrid-recommendation.md)
   的精神：算得出來或標示情境，不寫死。

## 5. 目標：首次使用旅程

```text
落地頁：「說一句話，生活的事就有人接手」→ 開始使用
   ↓
首次設定（30 秒內）：你住哪個社區／地區
   → 有明確用途：決定哪些服務可用、哪些廠商能服務你（不是為問而問）
   ↓
首頁（尚無任何紀錄，但不是空白）
   ┌──────────────────────────────┐
   │  今天需要什麼？                │
   │  ┌────────────────────────┐  │
   │  │ 例如：浴室的燈不亮了…      │  │ ← AI 輸入框是主動作
   │  └────────────────────────┘  │
   │  試試看：家裡有東西壞了 ·       │
   │         想找人打掃 ·           │
   │         社區這期有什麼團購      │
   └──────────────────────────────┘
   ↓
說出需求 → AI 判斷服務 → 題組引導填答 → 媒合廠商 → 成單
   ↓
有了第一筆之後，首頁才長出「進行中」與「該提醒你的事」
```

這條路徑讓「AI 理解需求並媒合」從側邊展示品變成**產品主動線**——那本來就是命題的核心
（「智慧社區服務需求理解與**媒合**平台」）。

## 6. 零狀態設計原則

| 畫面 | 有資料時 | 零狀態時 |
| --- | --- | --- |
| 首頁 | 進行中的事、可解釋推薦 | AI 輸入框＋三個真實情境起手式 |
| 訂單 | 訂單與進度 | 「還沒有任何委託」＋一鍵回首頁描述需求 |
| 社區 | 聯合服務、團購進度 | 「你的社區還沒有進行中的活動」＋可做什麼 |

**零狀態不是錯誤狀態**，它是新使用者看到的第一個畫面，要負責教學。

## 7. 三項分岔（已定案 2026-07-26）

### 分岔 A：四個工作區怎麼處理？→ **角色分離入口**

路徑結構定為 `/login`、`/user`、`/admin`、`/partner`。取消頂端的工作區下拉——
真實使用者只會是其中一種身分。詳見 [ADR-0015](../adr/0015-role-separated-entry-points.md)。

**平台營運（`/platform`）不列為主要角色**，與先前「平台營運者屬後續加分」的決定一致；
路由保留但不出現在登入選項與主導覽。

### 分岔 B：新使用者是空的，demo 怎麼展示豐富資料？→ **兩種都是真的**

新帳號**真的空**，由零狀態負責教學；官方訂單資料中的帳號則是「已經用了一陣子的使用者」。
切換的是**登入身分**，不是 demo 開關。詳見 [ADR-0015](../adr/0015-role-separated-entry-points.md)。

### 分岔 C：首頁主動作是什麼？→ **自然語言輸入框**

住戶首頁的主動作是「今天需要什麼？」輸入框，服務目錄退為次要入口。
詳見 [ADR-0016](../adr/0016-conversation-first-home.md)。

## 7.5 第二輪回饋（2026-07-27）：AI 感受不到、UI/UX 不合格

實際試用後的兩項判斷，皆屬實：

**① AI 做的事，一個表單都做得到。** 全系統只有兩個 LLM 呼叫點（意圖分類、欄位抽取），
且送出後的每一步都是人點按鈕——AI 在按下送出的瞬間就下班了。
→ 決策見 [ADR-0017](../adr/0017-llm-plans-rules-execute.md)：LLM 規劃、規則執行，
能力即 MCP 工具。

**② WCAG AA 與 RWD 只做到「測試會過」，不是體驗良好。** 193 行手寫 CSS、無設計系統，
且從未實際在 390px 檢視。
→ 決策：前端每次動工都必須用 `ui-ux-pro-max` skill，並實際檢視 390／1440 兩個斷點；
不另外排「UI 美化」的獨立階段。

### AI 能力建置順序（已定案）

| 順序 | 能力 | 狀態 |
| --- | --- | --- |
| **1** | **需求側主動性** | 今日摘要 ✅（`core/insights/today.py`）／一句話多意圖拆解 ✅（`agent/planner.py`）／事件觸發推播 ⬜ |
| **2** | 供給側生產力 | ⬜ 廠商報價草稿建議、管委會團購企劃與公告 |
| **3** | 服務缺口飛輪 | ⬜ 從未被滿足的需求累積出「該招什麼廠商」的平台情報 |

全部以 MCP 工具形式實作，同時滿足命題的 MCP Server 交付要求
（`mcp_server/`，12 項能力，與規劃器共用同一份註冊表）。

### 已補上的官方核心

**FR-S-04 服務媒合**（P0，先前完全未做）已於 `core/matching/vendors.py` 實作：
依命題明列的七項條件（服務類型／地區／時段／預算／緊急程度／可服務範圍／評分）
列 2–3 家比較，每家附加分理由與不符合的代價，可改選。

### 第二輪回饋的兩項判斷，現況

**① AI 做的事，一個表單都做得到** → 已改變。規劃器會把一句話拆成多個步驟，
使用者看得到系統理解了什麼、動用哪項能力、依據是什麼；寫入動作停在待確認。

**② WCAG AA 與 RWD 只做到「測試會過」** → 流程已改變：每次動前端都實際開瀏覽器
檢視 390／1440，`npm run audit:ui` 會檢查橫向溢出、觸控目標、console 錯誤，
以及**標題被吸頂導覽蓋住**（這一項是實測才發現、橫向溢出檢查抓不到的）。

## 8. 影響範圍（決策後的工作量預估）

| 區域 | 變更 |
| --- | --- |
| 路由 | 新增落地頁與首次設定；`/` 不再直接跳儀表板；角色入口分離（依分岔 A） |
| App 外殼 | 移除工作區下拉與「重設」；導覽依身分決定 |
| 首頁 | 主動作改為 AI 輸入框；零狀態與有資料狀態分開設計 |
| 身分 | 引入「目前使用者」概念（可先為輕量假登入，但語意是登入而非 demo 切換） |
| 既有測試 | 掛載 App 的元件測試需跟著調整進入點 |

## 9. 驗收方式

**一個沒看過這個專案的人，在沒有任何口頭說明的情況下，能在 60 秒內完成第一件事。**

具體檢查：

- [ ] 打開首頁能說出「這個 app 是做什麼的」
- [ ] 不需要別人指路就知道第一步該點哪裡
- [ ] 全新帳號看不到任何不屬於自己的資料
- [ ] 畫面上每個數字都指得出來源（算出來的或標示為情境設定）
- [ ] 沒有任何只為 demo 存在的控制項出現在使用者面前
