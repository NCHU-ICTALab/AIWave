## 1. 官方問題與產品回答

官方要求以未來使用者視角打造「生活的 AI 管家」，涵蓋餐廳推薦、購物推薦、社區服務諮詢與媒合；消費者能以文字或語音描述需求，由 AI 判斷類型、產生彈性留資表單，合作廠商則在後台查看、聯繫及承接案件。合作廠商若提供 API，應可包裝為 MCP Server 供智慧管家調用。

AIWave 的回答是：

> **會員說出想完成的生活目標，AI 將跨點數、廠商與群組規劃、比較、確認、執行並追蹤到底。**

核心不是再做一個服務目錄，而是把分散的服務、優惠、表單與履約狀態變成一條可執行生活任務。

## 2. 產品邊界

### AIWave 負責

- 理解單一或多個自然語言需求，保留對話上下文。
- 將目標拆成有先後與相依關係的生活任務。
- 依服務、地區、時段、預算、緊急程度、範圍、評分、點數及優惠產生方案。
- 依權限直接讀取、導覽，或產生待確認的設定、表單及交易預覽。
- 經確認後調用平台 API／MCP，持續追蹤廠商接單及履約。
- 在會員同意後使用家庭或社區群組進行代辦、通知、需求聚合及共同排程。

### AIWave 不負責

- 重做 OPENPOINT 的完整帳號、支付、點數或活動平台。
- 重做社區管理費、門禁、包裹、公告或 AIoT 硬體系統。
- 取代實際服務廠商的派工及現場履約系統。
- 以 LLM 直接決定金額、點數、權限或訂單狀態。

完整競賽論述見[競賽策略](../strategy/competition-winning-strategy.md)。

## 3. 使用者與範圍

### 主要角色

| 角色 | 核心任務 | 產品入口 |
| --- | --- | --- |
| 會員 | 管理個人生活、點數、服務、訂單及群組 | 會員 Web／未來語音與 LINE 延伸 |
| 合作廠商 | 查看需求、報價、聯繫、承接及更新進度 | 廠商後台或廠商 API |
| 平台營運者 | 管理服務契約、接入狀態、服務缺口及稽核 | 平台後台 |

管理者不是會員端的另一個人格。家庭照顧者、宿舍幹部及社區管理者都是某個 `Group` 內帶有特定 role 的 `GroupMember`；同一人可以同時加入多個群組。

### Scope 規則

- `individual`：會員本人資料及操作。
- `group`：家庭、情侶、宿舍或社區共享資料。
- 每個 group 操作都要帶 `group_id`、成員 role 及 active scope。
- 分享個人需求、代辦、聚合與通知都要明確同意；加入群組不等於授權全部個人資料。

## 4. 會員端資訊架構

頁籤順序固定為：

1. **首頁**：點數、本月消費、待處理事項、輕量 AI、推薦、常用功能、活動。
2. **點數兌換**：點數餘額、優惠券、兌換、折扣／累點試算及紀錄。
3. **AI**：完整聊天與生活任務工作區，可掌握並操作全系統能力。
4. **服務**：可瀏覽、搜尋、比較並進入真實下一步的服務能力。
5. **會員中心**：個人資料、偏好、過敏／禁忌、群組、權限、通知與隱私設定。

訂單是跨頁能力：首頁顯示待處理摘要，會員中心或深層連結提供可折疊的完整清單與時間軸；AI 可直接開啟指定訂單。

## 5. 三個招牌能力

### 5.1 生活目標編排

一句話可以包含多個意圖。Planner 產生結構化任務步驟、相依關係、缺少資料、可用工具及確認層級；工具白名單驗證後才能執行。

### 5.2 跨服務最佳方案

確定性規則計算價格、點數、優惠、服務範圍、排序及限制；LLM 將結果轉成自然語言並說明取捨。推薦必須可單張操作，「不感興趣」只影響該項及相似偏好，並可復原，不能關閉全部推薦。

### 5.3 確認後執行到底

| 操作層級 | 範例 | 預設行為 |
| --- | --- | --- |
| 讀取／導覽 | 查點數、查訂單、切到頁面 | 可直接執行並顯示依據 |
| 設定／表單 | 填地址、建立提醒、產生諮詢單 | 先顯示變更預覽 |
| 交易／高影響 | 下單、兌換、接受報價、取消 | 明確確認後執行並寫入稽核 |

## 6. 代表性情境

### Hero：爸媽週六要來

會員說：「爸媽週六要來，浴室燈壞了、冷氣也很久沒洗，幫我安排一下，OPENPOINT 能省就省。」

AI 拆解修繕、清潔、時程及點數最佳化；必要時詢問少量缺失資料；比較王子水電及清潔方案；產生一次確認摘要；確認後建單並追蹤。若會員同意，可詢問家庭或社區是否有相同需求以取得共同時段或方案。

### 官方核心覆蓋

| 官方要求 | AIWave 流程 |
| --- | --- |
| 自然語言／語音描述 | 全頁 AI 對話；語音為後續同一輸入契約 |
| 意圖判斷 | 多意圖 Planner＋服務候選排序＋低信心澄清 |
| 彈性留資表單 | 官方題型 schema 驅動的題組引擎，可由聊天或表單完成 |
| 餐廳／購物推薦 | 情境、偏好、點數與優惠共同排序，卡片可直接操作 |
| 社區服務媒合 | 七項條件的可重算媒合＋群組需求聚合 |
| 廠商後台 | 案件摘要、報價、回覆、狀態及履約事件 |
| 廠商 API／MCP | OpenAPI fake server、`VendorClient` seam、MCP tools |

## 7. 供給生態與資料原則

- 第一版優先使用公開可驗證的統一體系或合作情境，例如太子物業、王子水電、DUSKIN、黑貓、foodomo、7-ELEVEN、康是美與博客來。
- 實際可用品牌以 OpenAPI fake server seed 與來源註記為準；不使用競業、不創造怪異公司名。
- 模擬能力只代表比賽允許的廠商 API 情境，不宣稱為正式即時合作 API。
- 官方訂單、題型、服務來源及地區資料必須保留 provenance；使用者畫面只顯示完成任務需要的資料。

## 8. 交付優先順序

1. 會員身分、首頁、點數、AI、服務、會員中心的真產品骨架。
2. Hero 生活任務從自然語言到確認、廠商接單及追蹤的完整閉環。
3. Vendor OpenAPI、獨立 fake server、Client seam、錯誤／降級測試。
4. 群組角色、同意、共同需求與通知。
5. 服務缺口情報、廠商擴張及 LINE／語音延伸。

功能只有在能進入招牌閉環、增加可信證據或直接對應官方要求時才升為 P0。
