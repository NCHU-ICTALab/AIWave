# AWS 以體驗速度為第一優先，規格從寬

競賽的 AWS 額度由主辦方提供，不是我們的成本中心。因此 AWS 選型的目標函數改為
**評審操作時的體感速度**，而非省錢；在速度與成本衝突時，一律選速度，規格開好一點。

這條**取代** [ADR-0004](0004-local-first-aws-portable.md) 結語中「serverless 對應尖峰離峰與成本」
的論述基調——移植策略（介面隔離、容器化）不變，但**選型偏好從「省」改為「快」**。

## 為什麼這不只是花錢

評分表有「完成度 15%：功能完整，**使用體驗良好流暢**」，而命題明訂評委「以使用者的角度去體驗」。
一個 3 秒冷啟動的首頁，在評審眼中不是「省成本的架構」，是**卡頓的產品**。
主辦既然提供額度，把額度換成延遲就是最直接的分數轉換。

## 選型偏好（速度優先版）

| 能力 | 省錢作法（不採用） | **本專案採用** | 理由 |
| --- | --- | --- | --- |
| API 執行單元 | Lambda 隨用隨啟 | **ECS Fargate／App Runner 常駐**，或 Lambda 開 **provisioned concurrency** | 冷啟動直接打在第一印象上 |
| 資料庫 | Aurora Serverless v2 最小 ACU 0.5 | **最小 ACU ≥ 2**（或直接 provisioned） | ACU 0.5 起步會有暖機延遲 |
| LLM | 地端 Gemma／小模型 | **Amazon Bedrock（Claude）** ＋跨區推論 | 抽取與規劃品質直接決定「Agent 像不像樣」 |
| 前端 | S3 靜態網站 | **CloudFront ＋ S3** | 邊緣快取，首屏時間 |
| 對話 session | 行程內記憶體 | **ElastiCache／DynamoDB** | 見下方後果 |

## Considered Options

1. **速度優先、規格從寬（採用）**——額度是主辦提供的，把它換成低延遲；體驗分數是評分表明列項目。
2. 成本優先的極簡 serverless——技術上正當，但在「額度免費」的前提下，是拿分數換一筆我們不用付的錢。
3. 全部開最大規格——浪費且無法自圓其說；「從寬」不等於無上限，仍要說得出每一項為何需要。

## Consequences

- **現在的 in-memory session 是移植阻礙。** `api/app.py` 把對話 session 存在行程內記憶體，
  一旦有第二個執行單元（常駐服務必然會有）就會話錯亂。移植前必須抽到
  `SessionStore` 介面，地端用行程內實作、雲端換 ElastiCache／DynamoDB。
- 簡報「為什麼這樣設計 AWS 架構」的答法改為：**架構決策的目標函數是使用者體感延遲**，
  並逐項說明哪個選擇消除了哪一段等待（冷啟動／DB 暖機／首屏／LLM 往返）。
- ADR-0004 的介面隔離紀律**不放寬**——正因為選型可能再變（Fargate ↔ Lambda），
  介面隔離才是讓這些選擇保持可逆的東西。
