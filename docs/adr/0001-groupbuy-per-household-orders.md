# 每戶跟團＝一筆 order_type 07 訂單

社區團購是自行擴充的功能，官方資料集只有訂單模型（`mms_order_record`）而沒有團購概念。我們決定：住戶每次跟團就產生一筆掛在自建「團購活動」下的 order_type 07（商城購物）訂單，以關聯表 `group_buy_order` 連結活動與訂單，不修改官方 DDL；結單時再將活動下所有跟團訂單彙總成給合作廠商的採購單。

## Considered Options

1. **每戶一筆 07 訂單（採用）**——既有的訂單查詢、狀態推播工具對跟團訂單一體適用（「我跟的芒果到了沒？」直接重用 `get_order_status`），且「延伸官方資料而非另起爐灶」的故事最順。
2. 一團一筆彙總訂單、住戶跟團只是明細——資料量少，但住戶查不到自己的跟團狀態，得另寫一套查詢與通知。
3. 完全自建 schema 不對應 07——自由度最高，但失去訂單工具重用性，與命題資料的銜接故事也難講。

## Consequences

- 團購到貨等狀態變更走訂單狀態機（`order_status`），推播服務不需要為團購另開分支。
- 結單彙總（採購單）是唯一的團購專屬邏輯，收斂在「結單」這一個動作裡。
- 一檔活動會產生 N 筆訂單，管理者儀表板的訂單統計需注意排除或分類 07 訂單以免灌水。
