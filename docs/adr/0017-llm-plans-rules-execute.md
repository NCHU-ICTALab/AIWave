# LLM 負責規劃，規則負責執行；Agent 能力即 MCP 工具

使用者實際試用後的判斷：「Agent 一點都不智慧」。盤點屬實——整個系統只有兩個 LLM
呼叫點（意圖分類、欄位抽取），**兩者都能被一個下拉選單加一組表單取代**，所以 AI 的
貢獻在體驗上完全不可見；而且送出諮詢單之後的每一步（報價、確認、完工）都是人點按鈕，
**AI 在按下送出的那一刻就下班了**。

決定把 Agent 從「填欄位的工具」升級為「會編排的助理」，但**不交出安全性**：

- **LLM 規劃**：拆解使用者意圖、決定要呼叫哪些能力、以什麼順序、缺什麼資訊要先問。
- **規則執行**：每個被呼叫的能力仍是確定性程式——金額試算、狀態轉換、資料寫入都不經
  LLM，維持既有的「AI 提議、規則把關」保證（[ADR-0002](0002-shared-form-engine.md)、
  [ADR-0011](0011-explainable-hybrid-recommendation.md) 的一貫立場）。
- **能力即 MCP 工具**：規劃器呼叫的每一個能力就是一個 MCP tool。這同時滿足命題明文的
  交付要求（「包裝成符合標準的 MCP Server，以利 Lumine one 等外部 Agent 調用」），
  不必為了 demo 和為了交付各做一套。

## Considered Options

1. **LLM 規劃、規則執行（採用）**——真的會編排（一句話多件事、跨服務、主動彙整），
   但金額與寫入永遠由規則決定。工具邊界乾淨，順勢就是 MCP。
2. 完全自主的 tool-using agent（ReAct 自由循環）——最「智慧」，但行為不可預測，
   demo 當場可能跑歪；且金額相關操作交給模型自由決定，風險與我們的可信敘事衝突。
3. 維持現狀只加固定流程——最安全，但「AI 不智慧」的問題原封不動，且無法回答
   「技術創新在哪裡」。

## Consequences

- 需要一個規劃層：輸入是使用者訊息＋當前狀態，輸出是**結構化的步驟清單**（要呼叫哪些
  工具、參數為何），而不是自由文字。步驟清單本身可以顯示給使用者確認。
- 規劃結果必須以工具白名單驗證：模型指定不存在的工具或參數不合法時，整個計畫作廢並
  退回可理解的說明，不允許「部分執行」。
- 既有的 `IntentAgent`（單一服務分類）是規劃層的退化情況，會被納入規劃器。
- 工具需要同時被 HTTP 與 MCP 曝露；因此工具定義（名稱、參數 schema、說明）要與實作
  綁在一起，避免兩份描述漂移——與題組定義單一來源的作法一致。
